# Security Review Oktober 2026 (#74)

Systematische Prüfung von Server, SPA und Deployment vor „Stable“. Methode: Code-Review entlang der Bereiche unten, Hypothesen mit Tests gegen `createTestApp` bzw. Playwright verifiziert; `pnpm audit` (keine bekannten Schwachstellen). Funde mit Schweregrad und Status; Regressionstests sind jeweils genannt.

## Threat Model

| Akteur | Ziel | Annahmen |
| --- | --- | --- |
| Angreifer im Netz | Sitzungen stehlen, Daten mitlesen | Referenz-Deployment nur über SSH-Tunnel/`127.0.0.1` (ADR 0010); bei Betrieb hinter TLS-Proxy `COOKIE_SECURE=true`. |
| Anderer registrierter Nutzer | Fremde Workspaces lesen/ändern, Server lahmlegen | Registrierung standardmäßig nur für das erste Konto; bei offener Registrierung sind andere Nutzer nicht vertrauenswürdig. |
| Präparierte Daten | Code im App-Kontext ausführen | Inhalte kommen per Sync von eigenen Geräten oder per Import aus Dateien: alles gilt als nicht vertrauenswürdig. |
| Mitnutzer eines Geräts | Lokale Kopie lesen | Lokale Daten liegen unverschlüsselt im Browserprofil (siehe unten); Schutz durch Betriebssystem/Profil und „Lokale Daten löschen“ beim Abmelden. |
| Betreiber | – | Vertrauenswürdig: hat Zugriff auf Datenbank, Anhänge und Schlüssel. Keine Ende-zu-Ende-Verschlüsselung (Nicht-Ziel des MVP). |

## Geprüft ohne Befund

- **Autorisierung:** Alle Routen außer Health/Ready/öffentlichem Auth hinter `requireAuth`; jede Workspace-Abfrage über `owner_id`. Sync-Push gegen fremde Workspaces, Dokumente, Blöcke, Tags, Geräte und Konflikte getestet – alles abgelehnt (`not_found`, `device_not_active`, `workspace_not_found`). Anhänge, Historie, Suche, Import und Push auf das eigene Konto beschränkt; Speicherpfade nur aus UUIDs.
- **Authentifizierung:** scrypt (N=2¹⁵, r=8, p=1, 16-Byte-Salt), zeitkonstanter Vergleich, Dummy-Hash für unbekannte Konten, gleiche Antworten; Sitzungstoken 32 Byte zufällig, nur SHA-256 gespeichert; Cookie `HttpOnly; SameSite=Strict; Path=/api`; Passwortänderung beendet andere Sitzungen.
- **CSRF:** `SameSite=Strict`; Formular-Content-Types werden abgelehnt (415), `text/plain` scheitert an der Validierung; keine CORS-Freigabe.
- **XSS im Editor:** keine `innerHTML`/`v-html`/`eval`; Links nur `http(s)`/`mailto` (`isSafeHref`), Einfügen nur als Text; Suchtreffer, Verlauf, Konflikte, Tags und Dateinamen nur als Text.
- **Anhänge vom Server:** nicht-Raster als Download mit `nosniff` und `CSP: sandbox`.
- **Push:** Payload ohne Inhalte, nur HTTPS-Endpoints aus der Allowlist, keine Redirects, Timeout.
- **Logs/Metriken:** keine Passwörter, Tokens, Cookies oder Bodies; Metriken nur Routen-Templates, nach außen von nginx gesperrt.
- **Service Worker:** cacht nur die App-Shell, nie `/api`.
- **Export/Import:** Dateinamen bereinigt; ZIP-Reader ohne Dekomprimierung, mit Pfad-, Größen- und CRC-Prüfung; Prüfsummen und Schema vor dem Import.

## Lokale Daten (unverschlüsselt im Browserprofil)

| Ort | Inhalt |
| --- | --- |
| IndexedDB `notion-alt-<userId>` | Workspaces, Seiten, Blöcke, Tags, Zuordnungen, Links, Konflikte, Warteschlange mit vollständigen Änderungen, Anhang-Metadaten und -Inhalte; `meta`: Geräte-ID, Sync-Cursor |
| `localStorage` | `notion-alt.lastUser` (ID und E-Mail, kein Token), zuletzt geöffneter Workspace, aufgeklappte Seiten (IDs), Dateigrößenlimit, iOS-Hinweis |
| Cache Storage | nur die App-Shell (HTML, JS, CSS, Icons) |
| Cookie | Sitzung, `HttpOnly` (für Skripte unlesbar) |

Eine abgelaufene Sitzung sperrt die lokalen Daten bewusst nicht (local-first, ADR 0009). Auf gemeinsam genutzten Geräten beim Abmelden „Lokale Daten auf diesem Gerät löschen“ wählen.

## Offene Punkte

- GitHub Actions per Commit-SHA pinnen, Container-Image-Scan in CI.
- Einheitliche Grenze für `ATTACHMENT_MAX_MB` und nginx `client_max_body_size` (derzeit manuell abzugleichen, dokumentiert).
- HSTS erst mit der HTTPS-Entscheidung (ADR 0011).
